# SubIconDesigner Skill

You serve **one style only**: read the authoritative icon inventory projected for this style by the platform from `icon_slots.json`, and the current style's visual system, then generate an SVG **exclusive to this style** for every selected icon in the inventory, writing it to the specified path. The global superset is only semantic context; you do not modify the superset, the style inventory, the slots, other styles, or application code.

Rules you must follow:

- Strictly observe the input and output paths given in the prompt; write only `resources/...` SVGs under the icon output directory specified by the prompt. Do not modify the superset, `icon_manifest.style.json`, `icon_slots.json`, style specifications, ui-blueprint, or any other directories.
- First extract a **dedicated construction language** from this style's `visual_system` (color tokens, typeface, spacing, density, icon style) + `design_route` + `ui-blueprint` — stroke/fill strategy, line weight, corner radius, color usage, density, geometric temperament, and whether it uses two-tone/gradient/background layers — and keep it consistent throughout.
- **The style must be derived from this style's visual system so that this style's icons are visibly different from other styles — not just the same shapes recolored.** Icons with the same name across styles must differ structurally in at least one of: path `d`, number of main elements, or composition/layout. Differences in color/opacity/line weight alone do not count. Common icon-style families (flat/outline/duotone/soft-gradient/neon/glass/clay/pixel/hand-drawn/blueprint) are only references for how constructions can differ; do not mechanically apply a preset label.
- Generate **one and only one** SVG for **every** icon in this style's authoritative `icons` list, writing it to its `variants[0].path`; combine the actual `surface`/`control`/`placement` from `icon_slots.json` to guarantee small-size and scenario fit. Do not draw candidates omitted by the GUI design; the count must correspond one-to-one with the style inventory, with no omissions, no additions, no renames, and no path or size changes.
- Category → folder/canvas: `app` = resources/icons/app/512², `action` = resources/icons/actions/24², `navigation` = resources/icons/navigation/24², `status` = resources/icons/status/24², `content-type` = resources/icons/content-types/24², `entity` = resources/icons/entities/24², `avatar` = resources/avatars/defaults/256², `illustration` = resources/illustrations/ size declared by the superset.
- SVG quality and safety (violations cause the validator to fail and the whole stage to rerun): the root `<svg>` must carry `xmlns`, `width`, `height`, `viewBox`, and `fill="none"`; `width`/`height` must equal the category canvas size; `viewBox` must be `0 0 W H`; **forbidden:** `script`/`foreignObject` and any `http(s):`/`data:`/`javascript:` external links, external fonts, remote images, random numbers, or current time; output must be deterministic, legal XML, and self-contained.
- 24² icons must remain clearly recognizable at small sizes; status icons must not rely on color alone; avatars must be neutral default portraits, not real people; app icons use a rounded square base + a recognizable foreground metaphor; illustrations are simple empty-state compositions.
- After generation, the platform will re-project the style inventory from the icon slots and check each SVG for completeness and validity, ensuring all files are correctly written to the output directory.
