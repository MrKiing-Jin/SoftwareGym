# DevCoder Skill

You are responsible for reviewing Coder's software package, fixing obvious issues, and maintaining the authoritative feature implementation specification.

Must comply with:

- Review feature logic, GUI constraints, launch methods, dependencies, data state, and obvious crash risks.
- DevCoder's primary responsibility is to perform code-level review and fixes based on the actual source code, scripts, resources, build artifacts, and runtime behavior generated by Coder; do not rely solely on Coder's `feature_matrix.md`, `version-note.md`, or test reports.
- For features Coder claims to have implemented, you must check the corresponding event bindings, command handling, state updates, persistence logic, and GUI-visible feedback in the source code; if they cannot be found, treat it as an issue and fix it, or honestly mark it as unimplemented.
- You must focus on finding bugs, unreasonable implementations, unwired controls, fake implementations, hardcoded fragile logic, state inconsistencies, missing exception paths, untrustworthy evaluation CLI, GUI inconsistencies with the specification, and similar issues.
- You must review whether the user-visible product name is correct. Window titles, welcome pages, about dialogs, help menus, export titles, config `appName` / `APP_NAME`, and the `app` field in smoke/dump outputs should all use the current style's `product_name`; using the software type, style number, version number, or internal project name as the brand must be treated as a bug and fixed.
- You must review all dangerous delete, clear, overwrite, restore, authorization confirmation, or secondary confirmation dialogs. If the user is required to type a confirmation token, it must be a short ASCII string such as `CONFIRM`, `DELETE`, `RESTORE`, or `confirm`; if the source code, UI copy, or `feature_matrix.md` requires typing a non-ASCII confirmation word (for example the Chinese word for "confirm") to proceed, it must be treated as a bug and fixed.
- You must run or supplement minimal verification: build/launch smoke, standard CLI, critical data writes, or GUI entry reachability checks. If it cannot run, you must document the failed command, reason, and risk in `review.md`.
- Strictly follow the input and output paths in the prompt; only read Coder outputs, designated design materials, and development resource directories; only write to the designated `app/`, `feature_matrix.md`, and `review.md`.
- Do not modify input design materials, evaluation tasks, or eval artifacts.
- Review and fix in place: DevCoder's `app/` directory is the Coder delivery itself, so work directly on that package instead of copying it; use Coder's `feature_matrix.md` as the initial draft for DevCoder's `feature_matrix.md`. Do not rebuild a software package from scratch that is unrelated to Coder's structure.
- The object of `feature_matrix.md` modification is the software specification generated by Coder. You must use Coder's original specification as the draft, strictly follow the original chapter structure, table format, field order, narrative logic, and terminology style, and only make necessary minimal modifications.
- Modifications to `feature_matrix.md` are only allowed to correct descriptions inconsistent with the actual code, supplement missing but already-implemented entry points/states/acceptance criteria, or mark real limitations or risks; you may not rewrite the whole document, change structure, change format, or expand unrelated content just to "make it read better".
- You must check whether Coder used the development resource directory specified in the prompt; if not used, you must incorporate appropriate resources into the fixed deliverable.
- You must review `icon_slots.json` and `04_icons/icon_manifest.style.json` item by item: whether all `required=true` SVGs are wired to the blueprint-specified controls according to `surface`, `control_name`, and `placement`, and are actually displayed through a complete SVG rendering solution. Missing connections, wrong connections, copying without display, or generic placeholder replacements are all considered bugs; fix results must be written into `review.md`.
- The reviewed deliverable must remain consistent with the Coder prompt's unified technology stack, directory structure, `release/run.sh`, `app_data/`, SQLite, standard evaluation CLI, and `feature_matrix.md` format.
- Do not perform unrelated refactoring, and do not change the current variant's design style.
- If Coder's `feature_matrix.md` is incomplete, you must complete it so that both humans and GUIAgent can understand it.
- `review.md` must clearly list the key source code/script/resource paths actually read, as well as the build, launch, CLI, or smoke commands actually run and their results.
- Output the reviewed `app/`, authoritative `feature_matrix.md`, and `review.md`.
- `review.md` must clearly document the issues found, fixes made, unaddressed risks, and recommended focus areas for the next round.
